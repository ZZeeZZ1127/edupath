EduPath
AI-Powered K–12 to College Planning Assistant
Scoped Design Document  |  AWS Hackathon 2025
3 people  |  1.5 days  |  AWS beginners
Mission: Give every student — especially first-generation learners — the same quality of academic guidance that wealthy families pay thousands of dollars for.

Scope note: This document reflects the realistic hackathon build. Features are prioritized ruthlessly for a 5-minute demo. Anything not in the demo flow has been cut.
1. What We Are Building
EduPath is an AI-powered academic planning assistant that builds a persistent profile for each student and uses it to deliver personalized, grade-appropriate advice — from elementary school through college applications.

The core differentiator is memory. Unlike generic chatbots, EduPath knows the student — their interests, grade level, past inputs, and goals — and references that context in every response.

EduPath is split into two tightly integrated systems:

2. Two-System Architecture
EduPath’s product is organized around two distinct but connected systems. Each has its own AI behavior, data inputs, and user-facing output.

System 1 — Recommendation System
What it does: Reads the student’s profile from the database and generates a set of recommended tracks — each track is a curated path of opportunities (research programs, internships, colleges, etc.) with tasks of varying difficulty. The student selects one active track at a time; System 1 also re-evaluates and recalibrates difficulty whenever a major change occurs (e.g., a track is completed or aborted).

Inputs (from DynamoDB student profile)
Student name, age, and current grade level
Academic interests and strengths
Extracurricular background
Goals and milestones entered by the student
Conversation history (last 3–5 exchanges)

AI Behavior
Every recommendation must reference at least one specific detail from the student’s profile

Returns structured, actionable tracks (not generic advice). Each track’s difficulty is derived from its tasks’ individual difficulty values (0–100) and stored in DB as part of the current track status.
Quality bar: if the response could apply to any student, the prompt is not good enough
Difficulty recalibration: when a track is completed or aborted, System 1 re-evaluates using completion rate and application outcomes (accepted/rejected) to adjust the difficulty of the next set of recommended tracks

System 2 — Planning System
What it does: Once the student selects an active track (from System 1’s recommendations), the Planning System takes ownership: it collects application materials, tracks progress, and records outcomes (accepted/rejected). All progress and results are stored in the database. On major state changes — track completed or aborted — System 2 triggers System 1 to recalculate the next recommended tracks.

Full student profile from DynamoDB (same as Recommendation System)
Any previously generated plans (from S3)

Simplified Data Flow
Student logs in via Cognito (handled by Amplify UI component)
Onboarding form sends profile data to POST /profile → Lambda → DynamoDB
Chat sends student message → POST /recommend → Lambda retrieves profile from DynamoDB → calls Bedrock Recommendation prompt → returns personalized opportunities
Student selects an opportunity → POST /plan → Lambda builds Planning prompt with opportunity + full profile → Bedrock generates application plan → plan stored in S3 and returned to frontend

Key principle: One Lambda per endpoint. Keep it simple. No Step Functions, no queues. Just API Gateway → Lambda → DynamoDB + Bedrock.

System Prompt Structure
Every Bedrock call includes the following context from DynamoDB:
Student name, current grade, and age
Interests and strengths (entered during onboarding)
Last 3–5 advice exchanges (conversation memory)
Any milestones or goals the student has entered
For Planning System: the specific opportunity being planned for

The system prompt instructs Bedrock to: always reference the student by name, connect advice to their stated interests, be specific rather than generic, and match tone to the student’s grade level.

Quality bar: If Bedrock’s response could apply to any student, the prompt is not good enough. Every response must contain at least one reference to something specific in that student’s profile.

7. Demo Script
Persona: Maria, 17, Grade 11. First-generation college student. Her mom works two jobs as a nurse. She has never spoken to a college counselor.

Opening (30 seconds — before touching the screen)
“Maria’s mom works double shifts at the hospital. She has always wanted Maria to go to college — but she has never had time to figure out how. College counselors charge thousands of dollars. Maria’s school has one counselor for 400 students. So Maria is figuring it all out alone. EduPath is what we wish existed for her.”

Live Demo Flow (4 minutes)
Open EduPath — Maria’s profile is already loaded (pre-seeded in DynamoDB). Show the profile sidebar: Grade 11, interests in biology and debate.
Navigate to Recommendations tab. Type: “What should I be doing this year to prepare for college?” — Bedrock responds with biology competitions, debate tournaments, and hospital volunteering, citing her specific interests.
Bedrock also surfaces 3 college recommendations with match reasoning. Point out: “Notice it recommends pre-med programs — because it remembered she’s interested in biology.”
Student clicks “Build a Plan” on one of the college recommendations. Navigate to Plans tab.
Planning System: Bedrock generates a full application plan — required materials (essay prompts, rec letters, transcript), deadlines, and a step-by-step checklist specific to that school and Maria’s profile.
Point out the memory across systems: “This is not a generic checklist. It knows she needs a science teacher recommendation because of her biology interest. That’s the power of a persistent profile.”

Closing (30 seconds)
“Maria’s mom will never see EduPath. But if she did, she would know her daughter is not alone anymore. That is Build with Gratitude. We build because someone worked hard so we could learn to code. And now we are using that code to pay it forward.”
8. Likely Judge Questions
Question
Our Answer
How is this different from ChatGPT?
ChatGPT forgets you the moment the conversation ends. EduPath remembers you from Grade 1 through college — and it uses that memory across two coordinated systems: one to recommend what you should pursue, one to plan exactly how to get there.
Why not just use a school counselor?
The average public school has one counselor for 400 students. Private college counselors charge $2,000 to $10,000. EduPath gives every student counselor-quality guidance for free.
How does the Recommendation System know what to suggest?
It reads the student’s full profile — grade, age, interests, goals, and conversation history — and passes it to Bedrock with a prompt that forces specific, profile-referenced output. Generic responses fail our quality bar.
How does the Planning System know what materials are needed?
The planning prompt includes both the student’s profile and the specific opportunity (college, internship, program). Bedrock generates requirements tailored to that combination — not a generic checklist.
How do you handle data privacy for minors?
Cognito handles authentication so data is tied to a secure account. In production, we would add parental consent flows and store no PII beyond what students voluntarily enter. FERPA compliance would be a next-step requirement.
What would you build next?
Interactive progress tracking in the Planning System, document ingestion via Textract so students can upload transcripts, a parent dashboard, and a teacher view. The architecture already supports this — we scoped it out for the hackathon timeline.
Which track are you submitting under?
We qualify for all three. Our strongest case is Bedrock track — Bedrock powers both systems — but the serverless architecture is equally strong.
